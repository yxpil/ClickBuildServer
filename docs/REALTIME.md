# 实时游戏服务（Phase 4）需求与设计底稿

> 状态：**未开工，需求已登记**。当前生成器只有 REST + SSE；下面是长连接、协议、房间同步、可靠性和生成器侧要补的完整范围。总路线见 [路线图-实时游戏服务.md](路线图-实时游戏服务.md)。
>
> 原则：先做“能跑一局”的最小闭环，再谈多实例与跨服。不要把所有能力一次塞进同一个 Node 进程。

## 0. 现状与边界

已有、可直接复用：

- 账号登录、`onlyId` 会话、token、RBAC、操作日志、限流、文件存储、审计。
- Redis `PUBLISH/SUBSCRIBE` 频道；但没有“频道消息 → 具体连接”的出口。
- MySQL + Redis 旁路缓存；没有“内存态对象 + 定期落库”的房间层。
- Go / Rust 原生生成骨架，但还不是完整的实时网关/房间进程。

没有：

- WebSocket / TCP / KCP / QUIC 长连接。
- 握手、连接注册、心跳、空闲踢除、断线重连、离线补发。
- 消息号路由、二进制编解码、粘包拆包、协议 DSL。
- 房间状态机、tick 调度、帧同步/状态同步、房间级并发控制。
- 长连接压测、在线数/房间数/帧延迟等指标。

## 1. 传输与连接层

### 1.1 长连接网关

优先做 **WebSocket**（网页 / 小程序），再做 TCP，最后按客户端需要补 KCP / QUIC。

- 网关只负责连接、鉴权、心跳、编解码、转发；不跑房间逻辑。
- 同一套连接抽象支持 `ws` / `tcp` / `kcp` / `quic`，房间进程不感知底层传输。
- 连接对象至少包含：`connId`、`onlyId`、`userId`、`transport`、`remoteAddr`、`connectedAt`、`lastPongAt`、`subscriptions`、`metadata`。

### 1.2 连接生命周期

1. 握手：客户端带 `onlyId + token`（或一次性 ticket），网关校验签名、过期、封禁状态。
2. 注册：连接写入本地连接表 + Redis 连接目录（多实例时）。
3. 心跳：客户端 ping / 服务端 pong；超过 `heartbeatTimeout` 判死。
4. 空闲踢除：超过 `idleTimeout` 无业务消息，主动 close 并记录原因。
5. 断线检测：TCP/WS close、pong 超时、半开连接；统一发 `disconnect` 事件给房间进程。

### 1.3 断线重连

- 会话保持：`sessionId` 与 `onlyId` 绑定，重连时换绑新 `connId`，旧连接立即失效。
- 重连票据：短期一次性 `reconnectToken`，避免长期 token 暴露在 URL。
- 离线期间消息补发：每个订阅频道维护递增 `seq`；客户端带 `lastSeq` 重连，服务端从 `lastSeq+1` 补发，超过窗口则提示全量同步。
- 补发队列要有上限和 TTL，不能把 Redis 当无限收件箱。

### 1.4 连接与用户映射

- 一个 `onlyId` 可以有多端/多连接；默认策略可配：
  - `multi`：允许多端同时在线。
  - `single`：新连接踢旧连接。
  - `single-per-platform`：同平台单连接，跨平台共存。
- 踢下线要发 `kick` 消息并带原因（重复登录 / 管理员踢人 / 封禁 / 顶号）。
- Redis 连接目录：`conn:{onlyId}` 存 `connId -> instanceId`，TTL 跟随心跳；实例下线时批量清理。

### 1.5 网关横向扩展

- 连接落在哪台：网关实例注册到 Redis，连接目录记录 `instanceId`。
- 消息怎么路由：`onlyId` 一致性哈希选网关；或查连接目录点对点投递。
- 跨实例广播：Redis Pub/Sub 或 Stream；房间进程只订阅自己房间的频道。
- 网关无状态化：连接状态在内存，目录在 Redis；网关崩溃由客户端重连 + 连接目录 TTL 清理。

## 2. 协议层

### 2.1 编解码

- 第一版 JSON，保证可调试。
- 高频帧补：
  - MessagePack：实现成本低，适合对象帧。
  - Protobuf：强类型、体积小，适合协议 DSL 生成。
  - FlatBuffers：只在真的需要零拷贝/极致解包时再上。
- 编解码器接口：`encode(msg) / decode(buffer) / contentType`，按连接协商，不写死。

### 2.2 消息路由

消息头至少：

```
magic | version | msgId | flags | seq | payloadLength | payload
```

- `msgId` 是数字消息号，映射到 `module + action`。
- 服务端按 `msgId` 查 handler 表；未知消息号直接拒绝并计数。
- 请求/响应/推送用 `flags` 区分；响应带 `requestId` 关联。
- handler 返回统一 `{ code, data, error }`，由网关编码回包。

### 2.3 粘包拆包

- TCP 用长度前缀：`payloadLength` + payload；半包进缓存，凑够再解。
- 设置单帧上限（如 1MB），超限断开并记录。
- 二进制帧和文本帧分开处理；WS 不走长度前缀，TCP/KCP 走。

### 2.4 协议定义 DSL

在工作台里声明：

```yaml
module: room
messages:
  - id: 1001
    name: JoinRoom
    direction: C2S
    fields:
      - { name: roomId, type: string }
      - { name: ready, type: bool }
  - id: 1002
    name: RoomState
    direction: S2C
    fields:
      - { name: roomId, type: string }
      - { name: players, type: array, of: Player }
```

生成：

- 服务端 handler 注册表与类型。
- 客户端 TypeScript / Go / Rust 类型。
- JSON / MessagePack / Protobuf 编解码。
- 文档与消息号清单，重复号校验。

### 2.5 压缩与校验

- 大帧可选 gzip/br；小帧不压，避免 CPU 反噬。
- 帧尾 CRC32 或签名，防篡改；关键交易类消息加 HMAC。
- 压缩算法、CRC、签名都走协议配置，不散落在 handler。

## 3. 房间与实时同步

### 3.1 房间模型

状态机：

```
created -> waiting -> ready -> playing -> settled -> closed
```

能力：

- 创建/加入/离开/解散；房主转移；成员列表。
- 准备/开始/结束；匹配队列；房间密码/邀请码。
- 房间配置：人数上限、模式、地图、tick 率、是否允许观战。

### 3.2 房间态存储

三层：

1. 热态：房间进程内存对象（成员、帧、临时变量）。
2. 温态：Redis 快照/事件流，供跨进程读取和崩溃恢复。
3. 冷态：MySQL 结算记录、对战记录、回放索引。

落库钩子：

- 定时批量刷盘（如每 5s 或每 N 帧）。
- 关键事件同步持久化（结算、充值、道具扣减）。
- 房间关闭时强制落最终快照。

### 3.3 同步方案

**状态同步**（回合制、SLG、MMO 大世界）：

- 服务端权威，定时快照 + 增量广播。
- 客户端只做表现和预测，关键判定回服务端。
- 快照带 `version`，客户端丢弃旧版本。

**帧同步**（MOBA、格斗、RTS）：

- 客户端上传输入指令，服务端按 tick 广播。
- 确定性模拟，固定随机种子；掉线追帧从关键帧 + 后续输入重放。
- 需要回放文件和校验和，便于复盘/举报。

两种方案不要混在一个房间类型里；房间配置里明确 `syncMode: state | frame`。

### 3.4 tick 调度器

- 固定步长循环：20Hz / 30Hz（50ms / 33.3ms），按房间独立或全局时间轮。
- 每个 tick：收集输入 → 更新状态 → 生成增量 → 广播 → 定时落盘。
- 延迟任务：技能冷却、倒计时、结算延迟、匹配超时。
- 单 tick 超时要监控；连续超时降频或踢出异常房间。
- 运行时初始化钩子之外，增加 `onTick / onJoin / onLeave / onSettle / onCrash` 生命周期。

### 3.5 并发控制

- 同一房间操作串行化：房间级串行队列，避免多线程/多协程同时改状态。
- 房间级锁 + 乐观版本号；跨房间操作走异步消息。
- 关键资源（货币、道具）用数据库事务/行锁，不依赖内存锁。
- 所有写操作带 `requestId`，幂等去重。

## 4. 服务端主动推送

- WebSocket 双通道订阅：房间频道、个人频道、全服公告频道。
- 现有 Redis `PUBLISH` 可复用为跨实例总线；补一个 `channel message -> connId` 的出口。
- 推送模式：广播、群发、点对点。
- 离线消息与推送队列、未读计数；客户端上线后按 `seq` 拉取。
- 推送要有优先级和合并策略，避免公告刷屏挤掉关键帧。

## 5. 游戏业务模块

可直接复用：

- 账号登录、`onlyId` 会话、RBAC、操作日志、限流、文件存储、审计。

要新建：

- 背包/道具/货币：强事务、防超扣、幂等扣减、流水对账。
- 装备强化：概率表、保底、失败惩罚、版本化配置。
- 排行榜：Redis ZSET，按日/周/总榜；结算快照。
- 邮件/公告：附件、过期、已读、群发。
- 任务/成就：进度事件、领取幂等。
- 对战记录/回放：帧输入、关键帧、校验和、举报入口。
- 聊天频道：世界/房间/私聊，敏感词、限速、举报。

防作弊：

- 关键操作服务端校验，客户端只提输入。
- 输入合法性、速率限制、异常行为标记。
- 数值配置服务端下发，客户端不参与判定。

配置表：

- 数值/掉落/关卡配置加载，支持热更新。
- 配置版本号；房间创建时锁定版本，避免中途变更。

## 6. 可靠性与数据一致性

- 操作幂等：`requestId` 去重，断线重发不重复扣费/发道具。
- 落库时机：状态先内存，定时批量刷盘；充值/结算同步持久化。
- 宕机恢复：房间快照 + 事件日志；崩溃后从最近快照重建，重连续传。
- 跨实例事务：跨服邮件/道具走队列补偿，最终一致；关键资金仍走数据库事务。

## 7. 性能与部署运维

- 运行时：Node 适合 IO 网关；tick 计算和广播用 Go / Rust 房间进程，避免堵事件环。
- 水平扩展：房间粘性调度、跨服调用、服分组。
- 监控：在线数、房间数、连接抖动、帧延迟、队列积压、错误率、tick 超时。
- 压测：模拟大量连接 + 高频消息；现有 HTTP e2e 不够。
- 网关与业务分离：网关无状态，房间进程按房间分片。

## 8. 生成器侧要加的东西

1. 新模块模板：长连接模块、房间模块、定时任务模块。
2. 协议/消息定义编辑器：消息号、字段、方向、编解码器。
3. 内存态存储抽象：内存 Map + Redis 备份 + 落库钩子。
4. tick 调度器与延迟任务运行时。
5. WebSocket / TCP 连接管理内核。
6. 游戏案例模板：房间对战、聊天房间、排行榜、匹配。
7. 产物区分两种运行形态：业务后台服务、实时游戏服务。

建议的产物结构：

```
realtime/
├─ gateway/          # 无状态连接网关
├─ room/             # 房间进程（tick / 状态机 / 同步）
├─ protocol/         # 消息号、DSL、编解码
├─ state/            # 内存态 + Redis + 落库
├─ modules/          # 背包、排行榜、邮件、任务
└─ deploy/           # 多实例、房间分片、压测
```

## 9. 实施顺序与验收

### P0：单机一局能跑

- WebSocket 握手鉴权、连接注册、心跳、断线检测。
- 消息号路由 + JSON 编解码。
- 房间创建/加入/离开/准备/开始/结束。
- 内存房间态 + 定时落库。
- 20Hz tick + 状态同步。
- 单机压测：1000 连接、20Hz 广播，事件环不堵。

验收：两个客户端进同一房间，准备/开始，服务端广播状态，断线重连能回到房间。

### P1：可靠与可运营

- 离线补发、`seq`、幂等 `requestId`。
- Redis 连接目录、跨实例房间频道。
- 背包/货币/排行榜/邮件/聊天。
- 管理端：在线数、房间数、踢人、公告。
- 压测 5000 连接 + 房间分片。

### P2：多实例与帧同步

- 网关水平扩展、一致性哈希/连接目录。
- 房间粘性调度、跨服队列补偿。
- 帧同步、回放、掉线追帧。
- TCP/KCP/QUIC、Protobuf/MessagePack、协议 DSL 生成。
- 监控指标、告警、混沌恢复。

## 10. 待拍板

- 网关/房间主语言：Go 还是 Rust。建议网关先 Go（生态和运维简单），tick 密集房间可选 Rust。
- 第一版同步方案：状态同步先做，帧同步后做。
- 房间进程部署形态：单进程多房间，还是每房间独立进程/协程。
- 消息总线：Redis Pub/Sub 起步，Kafka/RabbitMQ 后补。
- 协议 DSL 的语法：YAML 先做，Protobuf `.proto` 作为导出格式之一。
